# APP 导航与视觉方向规范｜三方向差异化 · 底部导航 · 组件视觉交付（全局默认，单一真源）

> 适用：凡面向用户交付的 APP（Android／iOS／Flutter／RN／Web／纯 HTML）。非 APP 项目不适用。
> 与 `app-theme-i18n.md`（主题＋多语言）、`app-brand-assets.md`（命名/图标/启动画面）并列，**三者不互相覆盖**。
> 本规范只写"必须怎样"，不新增 Skill、角色、PROJECT_PHASE 状态或 Human Gate——全部挂既有 Gate。

## 0. 默认继承与覆盖

面向用户的 APP **自动继承**本规范，不反复问用户。只有用户对某项目明确提出特殊要求，才在该项目 `PRODUCT_PLAN`「APP 导航与视觉方向声明」记覆盖；**Planner／Builder／QA 不得自行取消默认要求**。

背景：本规范针对三类反复出现的失败——① AI 生成的 APP 风格高度雷同（只换配色）；② 导航组件由 Builder 临场随意设计；③ Android 底栏被放进可滚动内容、跟着内容滚走。

---

## 1. 视觉方向探索（三方向必须真正不同）

### 1.1 默认行为

新 APP 在**完整原型之前**，默认提供**三种真正不同的视觉方向**（A/B/C）。三方向不是可选项，也不是"先给一个再微调"。

### 1.2 硬性要求

1. **必须在同一个核心页面上做对比**：A/B/C 各自把**同一张核心页面**完整呈现，而不是各挑一个不同页面互相比。只有同一页面并置，差异才是可比的产品决策。
2. **必须逐轴拉开差异**，至少覆盖：布局结构、信息密度、**字体**（字族/字阶/字重策略）、**图标**（造型与线面风格）、**组件造型**（圆角、描边、阴影、控件形态）、**留白**（间距节奏与密度感）、品牌调性。
3. **只改配色＝没做方向**。若 A/B/C 的差别可用一句"同一套布局换个主色"概括，视为未做方向，按 `VISUAL_DIRECTION=BLOCKED` 处理。
4. **`LIGHT`/`DARK` 是已选风格的主题适配，不是两个独立设计方向**。浅色/深色渲染差异**不得**用来充当 A/B/C 的差异轴；每个方向内部才展示浅/深两态。

### 1.3 批准之后

用户批准某一方向后，**直接进入既有 Design Freeze 流程**，不得重复询问、不得重新选风格、不得在实现阶段"顺手优化"成另一种风格。方向变更属 Change C（核心产品方向变更），走 `PLAN_REOPEN_REQUIRED`。

## 2. 底部导航决策（不是所有 APP 都要 Tab）

1. `PRODUCT_PLAN` **必须明确**本 APP 是否需要底部导航，**并写明理由**。留空＝计划缺项。
2. **只有信息架构真正需要时才采用**。单一主任务、单屏工具、无并列任务集等，默认**不设**底部 Tab——不要为了"像个 APP"而硬加。
3. 采用底部导航时的记录项：入口**名称、数量、顺序**（见 §3）。

---

## 3. 组件视觉交付清单（禁 Builder 自行猜测）

采用底部导航或任何核心导航组件时，下列各项**必须在 UX Contract 显式写明，并在 Design Freeze 的 COMPONENT Freeze 绑定**。出现"开发者决定"「TBD」「按实现调整」等表述即视为关键行为未定义。

| 交付项 | 必填内容 |
|---|---|
| 入口 | 名称、数量、顺序 |
| 图标 | 资源、**线条或填充**风格、尺寸档位 |
| 状态 | **选中／未选中／点击／焦点**四态的视觉表现（含 pressed、focus-visible） |
| 排版 | 字体、字重、字距、间距 |
| 颜色 | 语义 Token（引用 `app-theme-i18n.md` 的 Token，不写死色值） |
| 显隐 | 导航显示与隐藏条件（如沉浸式页面是否隐藏） |
| 适配 | 小屏、**英文长文案**、系统手势区域（safe area／gesture inset） |

## 4. Android 底部导航实现规范

### 4.1 优先官方组件

对采用底部导航的 Android APP，**优先评估并使用官方 Material 3 组件**：`NavigationBar`、`NavigationBarItem`、`Scaffold(bottomBar = …)`。既有 Reuse Audit 仍按既定顺序确认版本／License／维护情况。**不新造导航框架。**

### 4.2 底栏位置铁律

1. 底栏属于**正常页面的固定导航位**；**滚动内容独立滚动**。
2. **禁止把底栏直接放进可滚动内容**（禁止 `Column` + `verticalScroll` 包住底栏；禁止把底栏塞进 `LazyColumn`／`RecyclerView` 的 item）。
3. 正确形态：`Scaffold` 承载底栏，滚动内容放进 `content` 作用域并消费剩余内边距（`innerPadding`），保证内容滚到底时不被底栏遮挡。
4. **沉浸式页面是否隐藏底栏，以产品批准的交互规则为准**（写入 UX Contract 与 COMPONENT Freeze），不得由 Builder 自行决定。

## 5. 各阶段前置检查（靠既有 Gate 拦截，不新增 Gate）

| 阶段 | 必做 | 拦在哪 |
|---|---|---|
| Product Plan | 写「APP 导航与视觉方向声明」：是否需底部导航＋理由；三方向差异化轴；导航各项交付 | Readiness／关键 AC 集合 |
| A/B/C 方向 | 同一核心页面并置对比；逐轴差异化；每方向浅/深两态 | Direction Gate |
| UX Contract | 底栏显隐规则、入口名/序/数、图标与四态、排版与 Token 显式化 | UX Gate |
| 原型 | 底栏固定不随内容滚动；必覆盖场景（见 §6） | Prototype Gate |
| Design Freeze | COMPONENT Freeze 绑定导航各项 + 底栏固定位 | Freeze Gate |
| QA | §6/§7 最小验证集 | 关键 AC 证据 |

## 6. 原型必覆盖场景（Human 2 前）

正式可点击原型**必须实际可操作地覆盖**：

- 滚动到**顶部、中部、底部**（并证明**底栏不随内容滚动**、内容不被遮挡）
- 页面切换
- 导航**显示与隐藏**（含沉浸式页面隐藏场景）
- 软键盘弹出／收起
- 系统安全区域（刘海、手势条）
- **浅色与深色**
- **中文与英文**代表性状态（含英文长文案）

---

## 7. QA 最小验证集

### 7.1 正式 Android QA 的证据要求

正式 Android QA **必须依据实际运行证据**判定：真机／模拟器**实际运行截图、录屏与交互测试**。

**禁止仅凭网页静态原型（或 HTML 原型）判定 Android 端视觉与交互通过**。网页原型只证明设计意图，不能替代 Android 实际渲染、真实手势、安全区域与系统交互的验证。

### 7.2 导航专项最小验证

- 底栏在长内容页滚动全程**位置固定**（录屏证明）
- 选中态随页面切换**正确同步**（截图证明）
- 沉浸式页面按批准规则**正确显示/隐藏**底栏
- 英文长文案下入口标签**不截断、不溢出**
- 系统手势区域**不遮挡**入口

## 8. 与既有体系的关系

- 本规范是**唯一真源**；UX Contract 与 Design Freeze **记录**其中的要求，**不另建一套真源**。
- 主题与多语言见 `app-theme-i18n.md`；命名／图标／启动画面见 `app-brand-assets.md`（本规范的"图标"项只管**导航入口图标**，应用图标仍归 `app-brand-assets.md`）。
- 阶段强制点挂在既有 Readiness／Direction Gate／UX Gate／Prototype Gate／Freeze Gate／关键 AC 上；**不新增 Skill、角色、状态或 Human Gate**。
